# Agent Workflow 使用教程

## 一、设计理念

### 1.1 为什么需要 Agent Workflow？

传统的 AI 辅助开发存在几个问题：

1. **单点瓶颈** - 一个 AI 处理所有任务，效率低下
2. **上下文丢失** - AI 记不住之前的决策和代码
3. **缺乏协作** - 多个 AI 窗口之间无法协调
4. **质量不可控** - AI 的自我评估不可靠

Agent Workflow 通过**文件驱动的异步协作**解决这些问题。

### 1.2 核心设计哲学

#### 人机分工明确

```
人类开发者                    AI Agent
─────────────────────────────────────────
决策者                        执行者
验证者                        编码者
裁判                          运动员
```

人类负责：
- 定义需求和目标
- 验证结果
- 做出决策
- 处理异常情况

Agent 负责：
- 编写代码
- 修复 bug
- 运行测试
- 更新状态文件

#### 文件即通信总线

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Agent A    │     │  PLAN.md    │     │  Agent B    │
│  (前端)     │────▶│  BUG-BOARD  │◀────│  (后端)     │
└─────────────┘     └─────────────┘     └─────────────┘
      │                   │                   │
      └───────────────────┼───────────────────┘
                          │
                    人类协调者
```

Agent 之间**不直接通信**，而是通过文件间接协作：
- 读取任务：从 PLAN.md 读取
- 完成任务：更新 PLAN.md 状态
- 发现问题：写入 BUG-BOARD.md
- 分配任务：人类决定分配给谁

#### 异步优先

Agent 之间**不互相等待**：
- Agent A 完成任务后更新文件
- Agent B 在自己方便的时候读取文件
- 不需要同步机制
- 人类作为协调者处理冲突

#### 质量先于速度

**永远不要信任 AI 的自我评估**：
- Agent 说"修复完成" → 你必须验证
- Agent 说"测试通过" → 你必须确认
- 每次修改都要测试
- 每次测试都要人工确认

### 1.3 为什么技术栈无关？

Agent Workflow 是一种**工作方法论**，不是具体工具：
- 核心是文件协作模式
- 不依赖特定语言或框架
- 通过 `project-config.md` 适配任何技术栈
- 用户自己定义文件范围和命令

## 二、项目阶段与场景路由

Agent Workflow 通过 **5 个场景** 覆盖项目全生命周期。系统会根据你的项目状态自动路由到对应的工作流。

### 2.1 场景总览

| 场景 | 阶段 | 条件 | 主导文件 | 工作流重点 |
|------|------|------|----------|------------|
| A: 新项目 | 规划期 → 开发 → 测试 → 上线 | 新项目 + 未上线 | PLAN.md | 从需求到发布的全流程 |
| B: 中途接手 | 探索期 | 已有 + 未上线 + 不熟悉 | PLAN.md | 先理解代码，再开发 |
| C: 迭代开发 | 开发期 | 已有 + 加新功能 | PLAN.md | 功能开发为主 |
| D: 测试修复 | 测试期 | 已有 + 测试阶段 | BUG-BOARD.md | Bug 修复为主 |
| E: 线上热修 | 维护期 | 已有 + 已上线 + 紧急 | BUG-BOARD.md | 紧急修复，最小改动 |

### 2.2 阶段转换流程

```
场景 A（新项目）
  │
  ├─→ 规划期 ─→ 开发期（场景 C）──→ 测试期（场景 D）──→ 上线
  │
  └─→ 如果中途接手 ─→ 场景 B（探索）──→ 场景 C ─→ 场景 D

场景 E（热修）←── 任何时候都可能触发
```

### 2.3 场景 A：新项目（全生命周期）

**适用情况**：从零开始的项目，需要完整的开发流程

**阶段划分**：
1. **规划期** - 需求分析、模块拆分、接口定义
2. **开发期** - 多 Agent 并行开发
3. **测试期** - Bug 发现与修复
4. **上线期** - 部署与监控

**PLAN.md 模板**：
```markdown
# 项目计划

## 当前阶段
规划期

## 需求列表
- [ ] 需求 1：
- [ ] 需求 2：

## 模块拆分
<!-- 按模块组织，每个模块分配给一个 Agent -->

## 接口契约
<!-- 前后端约定的 API 格式 -->
```

**工作流程**：
1. 你定义需求，写入 PLAN.md
2. 拆分为模块，分配给不同 Agent
3. Agent 并行开发
4. 定期集成测试
5. 进入测试阶段后切换到场景 D

---

### 2.4 场景 B：中途接手（探索期）

**适用情况**：接手已有项目，但不熟悉代码

**关键原则**：**先探索，不写代码**

**探索 Prompt**：
```
Read the entire project at [PROJECT_PATH].
1. Identify the tech stack and frameworks
2. Map the directory structure
3. Identify entry points
4. Find configuration files
5. Trace key user flows
6. Identify patterns and conventions used
7. Note any code smells or issues
8. Generate a project summary document
```

**工作流程**：
1. Agent 分析代码库，生成架构文档
2. 你理解项目结构和模式
3. 创建 PLAN.md 记录当前状态
4. 识别技术债务和改进点
5. 计划增量改进
6. 开始常规开发（切换到场景 C）

---

### 2.5 场景 C：迭代开发（开发期）

**适用情况**：熟悉代码，添加新功能或改进

**PLAN.md 模板**：
```markdown
# 项目计划

## 当前迭代目标
用户管理功能

## 任务列表
- [ ] [前端] 用户列表页面
- [ ] [后端] 用户 CRUD API
- [ ] [前端] 用户编辑表单

## 接口契约
POST /api/users - 创建用户
GET /api/users/:id - 获取用户
```

**工作流程**：
1. 更新 PLAN.md，明确本次迭代目标
2. 分配任务给对应 Agent
3. Agent 并行开发
4. 你验证每个完成的任务
5. 发现 Bug 走场景 D 流程

---

### 2.6 场景 D：测试修复（测试期）

**适用情况**：功能基本完成，专注于发现和修复 Bug

**BUG-BOARD.md 模板**：
```markdown
# Bug 看板

## 待修复 (TODO)
## 【前端】登录按钮点击无响应
## 【后端】API 返回 500 错误
## 【前端】样式在移动端错乱

## 修复中 (IN PROGRESS)

## 已修复待验证 (DONE)
```

**工作流程**：
1. 你测试应用，发现 Bug
2. 写入 BUG-BOARD.md，标注角色（【前端】/【后端】）
3. 切到对应 Agent："看 BUG-BOARD.md，修前端的那条"
4. Agent 修复，更新状态到 DONE
5. 你验证修复
   - 通过 → 清除条目
   - 失败 → 补充原因，打回重修
6. 每批修复后运行回归测试

---

### 2.7 场景 E：线上热修（维护期）

**适用情况**：生产环境出现紧急问题

**严重程度分级**：
| 级别 | 说明 | 响应时间 |
|------|------|----------|
| Critical | 服务宕机、数据泄露、安全漏洞 | 立即 |
| High | 主要功能不可用，无替代方案 | 1小时内 |
| Medium | 功能异常，有替代方案 | 4小时内 |
| Low | 次要问题，界面瑕疵 | 下个迭代 |

**热修 Prompt**：
```
URGENT: Production issue.
[问题描述]

Requirements:
1. Fix ONLY this specific issue
2. Minimal changes - no refactoring
3. Preserve all existing behavior
4. Run critical tests to verify
5. Document what was changed and why
```

**工作流程**：
1. 评估问题严重程度
2. Agent 做最小修改（不重构、不优化）
3. 运行关键测试（不是完整测试套件）
4. 立即部署
5. 记录修复内容
6. 安排后续完整修复（如果需要）

---

### 2.8 如何选择场景

**问自己这些问题**：

1. **项目是新的吗？**
   - 是 → 场景 A
   - 否 → 继续

2. **我熟悉这个代码库吗？**
   - 不熟悉 → 场景 B
   - 熟悉 → 继续

3. **现在是紧急情况吗？**
   - 是（生产环境问题）→ 场景 E
   - 否 → 继续

4. **主要工作是什么？**
   - 开发新功能 → 场景 C
   - 测试和修 Bug → 场景 D

**告诉 AI**：
```
我的项目处于 [场景名称] 阶段，请按照对应的场景工作流执行。
```

## 三、快速上手

### 3.1 第一步：安装

```bash
# 进入你的项目目录
cd /path/to/your/project

# 创建 .agents/skills 目录
mkdir -p .agents/skills

# 复制 agent-workflow
cp -r /path/to/agent-workflow .agents/skills/agent-workflow
```

### 3.2 第二步：配置

#### 方法 A：手动配置

创建 `project-config.md`：

```markdown
# 项目配置

## 技术栈
- 编程语言：Python
- 框架/库：Django
- 包管理器：pip

## 文件范围

### 后端 Agent
- 可修改文件模式：**/*.py, **/*.html, **/*.css
- 不可修改文件：*.js (如果有前端分离), docker-compose.yml
- 测试命令：pytest
- 构建命令：python manage.py collectstatic

### 前端 Agent（如果有）
- 可修改文件模式：static/**/*.js, static/**/*.css
- 不可修改文件：**/*.py
- 测试命令：npm test
- 构建命令：npm run build
```

#### 方法 B：AI 辅助配置

将 `config/setup-prompt.md` 中的 Prompt 发送给你的 AI：

```
请分析我的项目并生成 agent-workflow 配置文件。

项目路径：/path/to/your/project

请执行以下步骤：
1. 扫描项目目录，识别技术栈
2. 识别前端和后端文件类型
3. 查找测试配置和测试命令
4. 查找构建配置和构建命令
5. 识别关键配置文件
6. 生成 project-config.md 文件
```

### 3.3 第三步：初始化

告诉你的 AI Agent：

```
Set up agent workflow for my project at /path/to/your/project
```

AI 会自动：
1. 读取你的项目配置
2. 创建 PLAN.md 和 BUG-BOARD.md
3. 输出 Agent 窗口初始化 prompt
4. 提供操作指南

### 3.4 第四步：开始使用

1. **打开多个 Agent 窗口**
   - 前端 Agent 窗口
   - 后端 Agent 窗口
   - （根据项目需要）

2. **添加任务到 PLAN.md**
   ```markdown
   ## 任务列表
   - [ ] [前端] 实现用户登录页面
   - [ ] [后端] 实现用户认证 API
   ```

3. **分配任务**
   - 切到前端 Agent："读 PLAN.md，开发用户登录页面"
   - 切到后端 Agent："读 PLAN.md，开发用户认证 API"

4. **验证结果**
   - Agent 完成后，运行测试
   - 确认功能正常
   - 更新 PLAN.md 状态

## 四、日常工作流程

### 4.1 开发新功能

```
1. 你：更新 PLAN.md，添加新任务
2. 你：切到对应 Agent 窗口，分配任务
3. Agent：读取 PLAN.md，开始开发
4. Agent：完成后更新 PLAN.md 状态
5. 你：验证功能，确认无误
6. 你：标记任务完成
```

### 4.2 修复 Bug

```
1. 你：测试发现 bug
2. 你：写入 BUG-BOARD.md，标注角色
   ## 【前端】登录按钮无响应
3. 你：切到前端 Agent → "看 BUG-BOARD.md，修前端的"
4. Agent：读取 BUG-BOARD.md，修复 bug
5. Agent：更新状态到 DONE
6. 你：验证修复，确认无误
7. 你：清除条目
```

### 4.3 并行开发

```
1. 你：在 PLAN.md 中添加多个任务
   - [ ] [前端] 实现用户页面
   - [ ] [后端] 实现用户 API
   - [ ] [前端] 实现设置页面
   - [ ] [后端] 实现设置 API

2. 你：分配任务给对应 Agent
   - 前端 Agent：处理所有 [前端] 任务
   - 后端 Agent：处理所有 [后端] 任务

3. 两个 Agent 并行工作，互不干扰

4. 你：分别验证每个完成的任务
```

### 4.4 代码审查

```
1. 你：切到审查 Agent（或任意 Agent）
2. 你："请审查 [文件路径] 的最近修改"
3. Agent：执行代码审查，报告问题
4. 你：决定是否接受修改
```

### 4.5 状态汇报

```
1. 你：切到任意 Agent
2. 你："读 PLAN.md 和 BUG-BOARD.md，给我状态汇报"
3. Agent：读取文件，生成状态报告
4. 你：了解项目进展
```

## 五、进阶用法

### 5.1 模块化开发（中型团队）

当团队超过 5 人时，按模块组织：

```
PROJECT-ROOT/
  PLAN.md
  BUG-BOARD.md
  MODULES/
    module-auth/PLAN.md
    module-api/PLAN.md
    module-ui/PLAN.md
```

每个模块有专门的 Agent 负责。

### 5.2 Git 集成

使用 Git 分支隔离 Agent 工作：

```bash
# 前端 Agent 在自己的分支工作
git checkout -b feat/frontend-user-page

# 后端 Agent 在自己的分支工作
git checkout -b feat/backend-user-api

# 完成后合并
git checkout main
git merge feat/frontend-user-page
git merge feat/backend-user-api
```

### 5.3 所有权注册表（企业级）

对于大型团队，维护文件所有权：

```markdown
| 文件模式 | 所有者团队 | 审批人 |
|----------|------------|--------|
| src/auth/** | auth-team | Alice |
| src/api/** | api-team | Bob |
| src/shared/** | platform-team | Carol |
```

跨团队修改需要审批。

## 六、最佳实践

### 6.1 任务描述要清晰

**好的任务描述：**
```
- [ ] [前端] 实现用户登录页面，包含：
  - 用户名/密码输入框
  - 登录按钮
  - 错误提示显示
  - 响应式布局
```

**差的任务描述：**
```
- [ ] [前端] 做登录
```

### 6.2 一次只做一件事

让 Agent 一次只处理一个任务：
- 完成一个，再处理下一个
- 避免多任务切换导致的问题

### 6.3 验证要彻底

每次修改都要验证：
- 运行相关测试
- 手动检查功能
- 确认没有引入新问题

### 6.4 保持文件同步

定期检查 PLAN.md 和 BUG-BOARD.md：
- 及时更新状态
- 清理已完成的条目
- 保持文件整洁

### 6.5 不要信任 AI 的自我评估

Agent 说"修复完成" → 你必须验证
Agent 说"测试通过" → 你必须确认
Agent 说"没有问题" → 你必须检查

## 七、常见问题

### Q: Agent 修改了不该修改的文件怎么办？

A: 检查 `project-config.md` 中的文件范围是否正确。如果 Agent 越界，回滚修改并更新配置。

### Q: 两个 Agent 同时修改同一个文件怎么办？

A: 这说明文件范围定义不清晰。重新定义角色分工，确保每个 Agent 只修改自己负责的文件。

### Q: Agent 完成的任务质量不高怎么办？

A: 这是正常的。Agent 的输出需要人工验证和调整。不要期望一次完美。

### Q: 如何处理跨角色的任务？

A: 将任务拆分为子任务，分别分配给对应角色。或者使用"全栈"角色处理跨角色任务。

### Q: 项目很大，任务很多，如何管理？

A: 使用模块化组织（见 4.1），每个模块有独立的 PLAN.md。或者使用 Git 分支隔离。

## 八、设计理念总结

Agent Workflow 的核心价值：

1. **简单** - 只需要两个文件（PLAN.md 和 BUG-BOARD.md）
2. **通用** - 适用于任何技术栈和团队规模
3. **可靠** - 人类验证确保质量
4. **高效** - 异步协作提高并行度
5. **可扩展** - 从个人开发者到企业级团队

它不是一个复杂的框架，而是一种**工作方式**的约定。通过文件驱动的异步协作，让人类和 AI Agent 高效配合，共同完成软件开发任务。
